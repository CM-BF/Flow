# 架构改进研究 · 2026-10-05

状态：研究建议 / 未在 Flow 实测，不是新增功能已经实现，也不改 W01/D01 冻结契约。本记录由 Goal Owner 提供已读官方资料结论，Execution Lead 落盘并对照当前工程限制；研究不暂停 M1。关联 [plan](plan.md)、[status](status.md)，不是另一份独立执行计划。

## 1. 从任务闭环到多目标决策

M1 当前主要证明单任务及其执行闭环；后续还应明确“一个地方掌握多个目标并决策”的产品验收。建议并行 10 个任务的用户测试：在同一工作流看到重要变化、处理等待决策、原地展开证据，记录切换次数、重复问题、人介入时长。已有线性交互方向，这里新增的是验收口径；不为每个工具事件调用模型解释。此处尚无用户测试数据。

## 2. 多 agent 成本需要对照

[Anthropic 多 agent 研究系统文章](https://www.anthropic.com/engineering/multi-agent-research-system) 报告其自身 2025 年研究中的多 agent 使用约普通聊天 15 倍 tokens。它不是相对单 agent 的普遍倍数，也不说明 A2A 通信占比，不能当 Flow 测量值。

建议 M2 固定任务、模型与验收，对比单 agent、完整历史交接、引用/增量交接三组；同时报告成功率及每个验收通过交付的总成本，包括失败和重试。区分协调、检索、压缩、验证、解释占比和缓存读写；缺失 usage 保持 unknown。

## 3. Context 策略与失效语义

UI 按需加载不自动减少 LLM 上下文。任务包建议使用固定目标/约束/验收/写入范围/预算，加版本化引用与变化；按需发现工具 schema，在工具侧筛选原始大结果，引用可追溯原文。来源改变后，摘要与下游证据需要显式失效语义。

[Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 与 [MCP code execution](https://www.anthropic.com/engineering/code-execution-with-mcp) 支持这个方向；其例子中的收益不是 Flow 的收益。稳定前缀适合缓存，时间/进度放变化部分；动态 schema 也可能损伤缓存。原生 harness 自主管理 context 时先观测，不侵入重排。[工具与 prompt caching 文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching)。

## 4. 优先补齐 uncertain 核对路径

当前 M1 遇到失联或撤销后保留 uncertain attempt/session/capacity，不自动重跑未知写入，也没有 reconciliation Interface。M1 后建议优先设计查询实际副作用、确认停止、释放占用、安全恢复的受审计路径，不能以直接修改数据库状态代替。

[pg-boss 官方介绍](https://pgboss.io/introduction) 说明重试下 handler 可以多次执行。租约不能撤回在途副作用，更换调度器也不消除幂等责任。分别说明浏览器断线、中心重启、runner 崩溃三个承诺层级：当前 queued 受理可在中心重启后恢复，活动 adapter 遇到中心不可达会保守中断，不能把它描述为透明恢复。

## 5. 协议版本与可靠性边界

本次官方资料研究时 [A2A 最新规范为 1.0.0](https://a2a-protocol.org/v1.0.0/specification/)：3.3.1 Send Message 幂等为 MAY，messageId 不保证去重；3.7 允许重连缺失 status messages，不能把协议观察流当关键事实可靠账本。

[MCP 当前版本资料](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) 指向 2026-07-28；[Tasks 已为 io.modelcontextprotocol/tasks 扩展](https://modelcontextprotocol.io/extensions/tasks/overview)，不能继续把 2025-11-25 experimental Tasks 当当前。新扩展 tasks/get 轮询含最终结果，input_required 用 tasks/update，取消是合作式。实际接入前仍需核对固定对端版本与其支持能力。

后续维护 version + role + transport + capability conformance 矩阵，跟真实对端选版本，不强迫原生 harness 升级 SDK。本研究不引入 M1 协议适配代码。

## 6. Harness 与插件边界

保留 native 或 HarnessAgent 按 adapter 混用。[AI SDK harnesses 仍标记 experimental](https://ai-sdk.dev/docs/ai-sdk-harnesses/overview)。[Pi inline factories](https://ai-sdk.dev/providers/ai-sdk-harnesses/pi) 在 host Node 执行并禁用文件自动发现；npm 可安装不等于安全隔离或插件兼容。

建议明确执行位置、恢复级别（同进程/进程重启/跨机）、状态迁移与唯一压缩 owner，长会话固定版本。当前不因此铺开插件市场或微服务。

## 7. 容量拆分预算

100+ agents 应拆成会话、活跃 LLM、工具、查询和数据库连接等预算，按 provider/runner 分别限制。先做 128 会话的无模型负载，定位存储和事件瓶颈，再做少量真实模型对照。尚无 Flow 实际容量压测数据，不宣称 PostgreSQL 已够或不够。

## 补充研究与解释边界

[《Towards a Science of Scaling Agent Systems》v3（2026-04-08）](https://arxiv.org/abs/2512.08296v3) 覆盖 260 组配置、6 个基准，结果取决任务结构；工具密集或强顺序任务存在协调开销。不要引用早期 v1 的 180 配置或用绝对收益百分比概括 Flow。当前推论是 ready 的独立工作并行、协调事件尽量程序化；并发上限不是长期维持的运行目标。

[Anthropic Managed Agents（2026-04-08）](https://www.anthropic.com/engineering/managed-agents) 将 durable session、harness 与 sandbox Interface 分离，也区分原始日志和模型工作上下文。Flow 可借鉴按需分配执行资源、持久事实不随压缩删除；这不证明当前 native SDK 可无状态或跨机器恢复。

[Microsoft 人机交互设计指南](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/) 支持关注中断时机、相关信息和易纠错。本文提出的切换次数、重复问题、人介入时长，是 Flow 的设计推论，不是该研究对 Flow 的实测证明。
