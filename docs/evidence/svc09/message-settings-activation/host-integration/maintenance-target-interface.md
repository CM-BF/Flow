# Same-operation held target evolution

This is a new explicit trusted operator command, `rebindHeldPreviewTarget(request, {loadCurrentConfiguration})`. It does not extend generic CLI, bootstrap or resume. Existing refresh gains one explicit pending-Web-target consumer. The sole loader port is a function statically bound by the reviewed operator to the fixed **04da/cd27** installation's existing public loader; request JSON cannot carry configuration or a replacement loader. It retains original source identity, marker and token-hash validation. The candidate operator must bind the new leaf and the old loader's distinct Git/artifact source and hashes. No af51 helper is substituted.

The exact request contains directory, operationId, unique requestId, expected held version, canonical SHA256 digests of the full old operation/state/Web release, old backend descriptor, independent Web host descriptor (or null), and full new backend descriptor. Input identity is compared again under the existing preview lock. The old three-role process set is explicit; undeclared/missing roles reject rather than silently adopting a settings slot. This leaf has no slot activation or DDL.

Before opening a runner-row transaction, verify the new immutable backend, the old independent Web host, the new Web host selected from exactly the same new backend artifact, and the complete retained Web release against the new backend source/browser context. A missing release rejects before the old prepare API could build anything. Old reports are preserved; old-source reports are never renamed or treated as evidence for the new source.

Under the same preview lock and `flow.runners FOR UPDATE`, check the token hash, unchanged same operation/version in maintenance, zero incomplete/uncertain attempts, and each registered group's real stopped observation. `active=0` alone is insufficient. Recompare all three local digests before mutation. Preserve original operation/hold/resume keys and bounded old-to-new audit (max4 entries/64KiB). Only `maintenance.json` advances to `target-bound` with the new descriptor/source and a bounded pending `webHostTarget` intent. Its audit preserves the complete old Webhost and three process records; this command leaves state/config/Web release untouched. The existing fsync+exclusive-temp/rename primitive is reused, followed by directory sync/readback. No DB state or audit row is changed and old hold CAS is not replayed.

Result separates primary phase/code, pool/lock cleanup, write attempted/observed, and a possible target binding. A thrown write/commit/close is unconfirmed even when the new file is observed. No retry, rollback of private bytes, service start or resume occurs. A repeated old request rejects the changed operation rather than manufacturing success. The caller may proceed to existing refresh only after an independently accepted confirmed result and fresh maintenance/identity evidence; an on-disk target-bound phase alone is not successful closure. Interrupted persistence may leave the exclusive temp and remains KEEP for a separately reviewed recovery, never an automatic delete/rewrite.

`maintenanceRuntime` and `assertInstallationSource` already accept a verified pending operation target; no identity bypass or new source-root override is needed. The later actual refresh consumes the explicit pending intent before prepare/start, under its existing preview lock and a new read-only runner-row-lock transaction. It checks the same held version/operation, zero active/uncertain work, original state/release/operation digests and all three stopped records. It reuses the new artifact's existing public `inspectPreviewWebHostSource` after the bound operation has authorized that module's source. It durably writes state Web selection as **selected-stopped**, then marks the operation intent selected. The old process records remain intact. Partial writes or missing COMMIT acknowledgement throw; changed state with pending intent rejects a later ordinary refresh instead of silently progressing. No automatic replay or rollback is authorized.

The existing prepare now reads the selected NEW Webhost; its original policy-code qualification and the new backend remain intact. Immediately before existing start, selection records `starting`; only actual start completion stores `ready` and the SHA256 of the actual new `state.processes.web` JSON, using the original replacement record convention. No state is made to claim readiness in advance. Existing startup failure/stop/unknown rules remain. This new explicit target is single-slot/three-role only; no-intent refresh and multi-slot maintenance retain their original path. Resume retains the original CAS and is not part of rebind.

Retained reports are found separately for every page at the NEW backend source (including legacy context=null), then public asset validation runs. This does not create/rename reports, update the release pointer, build assets or assert App compatibility. A real candidate therefore still needs the new-source reports before rebind can succeed. Source assembly uses **04da + only the reviewed necessary recovery deltas**, not this worktree's newer slots/DDL. Actual new artifact, reports, operator assembly and personal execution remain subsequent reviewed boundaries.

Local checks use actual module code and original database transaction helper with synthetic Pool/process/runtime ports, plus private owned toy files using the actual existing save primitive. Separate real Node/tsx import and invalid-input checks perform no connection or installation I/O. They do not prove real PG locking, artifact inventory, process identity or personal recovery.

`maintenance-target-04da-input.json` and `.patch` bind the exact fixed04da maintenance-host preimage and its three localized insertions. A no-PG direct consumer applies those exact replacements to `git show` source, verifies before/after hashes and executes real refresh with synthetic external ports. This is an assembly input, not a whole-copy of current multi-slot main, not an artifact or personal result.
