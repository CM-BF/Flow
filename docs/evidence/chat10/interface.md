# CHAT10 frozen interface

- Trusted host reads `FLOW_ACTIVE_STEERING` using `parseActiveSteeringConfiguration(raw?: string): boolean` from `apps/server/src/active-steering-configuration.ts`. Absent or exact `0` → false; exact `1` → true; every other value throws without echoing input. F01 alone wires `main.ts`/`index.ts`; no HTTP enable option.
- Owner `GET /api/tasks/:id/steering/admission?attemptId=...` returns `SteeringAdmission` in `packages/contracts/src/active-steering.ts`; attempt defaults to current. Unknown or cross-task selected attempt is 404. `Cache-Control: no-store`.
- `state: ready` includes current `attemptId`, `ownerVersion`, `revision`. `unavailable` gives a bounded reason, with nullable metadata when no attempt/control storage is available. Off returns `disabled` without touching migration 024 tables. Enabled but missing installation returns `not-installed`.
- Readiness requires current running/uncompleted attempt, matching owner version, live lease, unrevoke runner, no decision, valid recorded native-session affinity, recognized enabled immutable profile, no final/seal/pending/unknown, and remaining command quota. GET is a repeatable-read/read-only snapshot, never creates a control/command/audit or reserves the next operation. POST checks again under existing locks; successful idempotent replay remains permitted despite its own pending command.
- Existing `SteeringState.attemptAvailable`, conversation `controls.steer` and public conversation capability remain unchanged. This is center admission, not SDK online/model compliance, personal deployment or UI enablement. No migration required; no new loop.

Known unavailability precedence is storage enablement, current ownership/liveness/profile, then final → command limit → seal → unresolved command. A selected old attempt may expose its own known revision, never another task's metadata. Consumers refresh after a failed POST; they must not treat a prior ready snapshot as a lock.
