# AV03 journal seam

This four-leaf slice is part of AV03, not the complete center/runner verification journey. `flow.runner-claim.v4` is a new strict request protocol. It positively carries verifier binding protocol, store, host API and the finite supported algorithm identities. Tool capability is a separate optional field with no default. Old v3 bytes and strict codec remain unchanged.

The actual consumer is the existing `AdmissionJournal`. `bindVerifierRunner` selects v4 only for a clean v1 snapshot; pending legacy intent/retained assignments do not select it, and v2/v3 requests cannot upgrade. Parsed detached input is captured before the shared serialized tail. Existing v4 requests bind only with exactly the same qualification and authenticated runner. Getters return copies. All older getters/binding APIs reject v4, so existing runtime callers cannot catch a null and silently downgrade.

`acceptOpportunity` now accepts the complete v4 request identity, validates the same key/runner/all capabilities, and persists assignment plus next key using the unchanged write→file.sync→rename→dir.sync→publish-memory order. Empty polls do not consume keys. Stale/changed acknowledgements and failed persistence never report acceptance. After uncertain persistence the caller must stop using that instance and reopen the same directory; this slice adds no retry, replacement identity or compensation loop. Completion removes only exact attempt/owner and retains protocol/qualification.

Journal remains bounded to64KiB and16 assignments. Capability has at most8 entries but the only currently supported algorithm is JSON-object required-keys version1 and duplicates are rejected. Thus current valid requests carry one algorithm; future algorithms require an explicit schema/algorithm change. These are accepted-data bounds, not a pre-parse hard memory bound for arbitrary caller objects.

This slice does not add HTTP response/assignment codecs, server routing, immutable binding-kind migration, source-project validation, SQL admission, phase grants, runtime dispatch or startup opt-in. No verifier task can be created by this slice. Future HTTP consumer must strictly validate the complete ACK before calling journal acceptance, and must complete the approved center/project/kind barriers before exposing v4 execution. Existing tool/legacy behavior is checked through two direct old tests, not by claiming the full old suite ran.
