## Smallest candidate injection change (design only; not implemented)
Prefer a bounded **after-headers truncated ACK body** fault. Keep the request, real center, status, key/body, and complete upstream capture intact. After receiving and recording a valid successful upstream JSON response, forward its real success status/content type and an explicit full Content-Length, no Transfer-Encoding/content encoding ambiguity, Connection: close/no-store. Forward a nonempty strict byte prefix of that original JSON, then close the owned downstream socket gracefully after the write callback. Never fabricate a successful JSON receipt, never send the complete body, and never change public request/ACK decoding. Prefix size and final close must remain bounded and tied to the same one-shot command. Inspect actual upstream headers before choosing framing; unsupported compressed/non-JSON/too-small or incomplete upstream data must fail the fixture rather than silently switch modes.

This targets the application's uncertain body-read outcome after headers, avoiding reliance on a pre-header stale-connection retry. A write callback proves local stream flush only, not browser receipt; future allowed execution must independently observe the selected response headers and the selected request/body-read failure, plus the actual Receipt unknown UI. If those observations do not occur, the fault injection is inconclusive, not product failure or green compatibility.

Keep the original strong behavioral assertions: exactly one pre-user-retry accepted POST for that armed key, original key/body/refs/turn recorded, actual unknown UI, next draft still present, then exactly one explicit Retry click and a real center replay with identical key/body/turn. Queue must use the same bounded injection and retain its own exact command/ref/new-draft assertions. The proxy can add per-injection framing/bytes/close records without credentials. This only changes fixture transport behavior; browser assertions and real accepted identities must not be weakened.

Alternative not preferred: an armed key/body fault held until explicit release. It would require strict per-key bounds and tracking every automatic resend; it complicates the existing exact two-POST expectation and risks hiding a product retry loop. Do not use an unlimited drop-until-green loop. Do not force legacy/plaintext, mock an ACK, modify products, or edit old raw to obtain unknown.
