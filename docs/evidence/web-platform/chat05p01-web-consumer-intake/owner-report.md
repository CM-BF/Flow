## Three concrete requirements for the existing Web follow-up

1. **One public read/validation seam, bound to the displayed observation.** Preserve the current private host reader and visibility/auth checks (`plugin-integration/activity.tsx:31–48`); pass expected task/attempt/activity from the trusted loaded row, not title or global activity string alone. A page must match the descriptor's immutable content identity and declared representation; validate page/chunk counts, base64-decoded byte lengths, ordered index/offset, digest and safe cursor progress before exposure. Keep whole-body verification separate: only a complete, fully assembled byte sequence may be called full-digest verified. UTF-8 can cross64KiB boundaries—do not independently decode every chunk with replacement characters or hash pretty-printed JSON. `nextIndex == receivedChunks` while receiving is explicitly legal (`contract:55–61`), not an empty-page failure or permission for a tight polling loop. Future direct consumers should cover wrong task/attempt, page identity drift, reordered/duplicate/corrupt chunks, split Unicode, receiving with no new tail, and legacy. These are future validation requirements, not claims about backend defects.

2. **Explicit demand and a bounded read cache, with existing lifecycle authority.** Current UI opens content on deliberate expansion (`NativeActivity.tsx:31–34`), and bindings deactivate on hidden/offline/mode/permission changes (`activity.tsx:53–78,92–96`). Keep that zero-body-before-expand behavior; descriptor first, user-requested chunk pages, no implicit full8MiB fetch from activity list/Terminal mount. Existing projection caches every opened body in `bodies` and retains loaded entries through deactivate (`projection.ts:18,66–68,104–120`); blindly placing full8MiB bodies there would not establish a cache bound. The consumer needs an explicit aggregate byte/entry/flight bound across its actual panes, accounting raw bytes plus retained base64/text/render copies; the server attempt limit is not a browser memory budget. Reuse one body-read state for the activity view and any body tab rather than duplicate readers. Keep abort and generation checks through decode/hash awaits and catch/finally; closing/revoking drops work, not task execution. Test late response/hash after hide/reopen/new attempt, eviction→explicit re-read, and no automatic tail draining. Do not claim current reply/queue cache limits already cover native bodies.

3. **An actual on-demand body destination with honest status and literal text.** Preserve real AI Elements Terminal for task output; don't append tool bodies into `task.entries` or relabel them as ordinary assistant output. A dedicated selected body view/tab may reuse Terminal shell/actions through its real `children` seam (`terminal.tsx:228–245`), keyed by exact task/attempt/activity and reached through the existing authorized host navigation. Native records currently stay in the message activity disclosure, so this requires an explicit future host/tab consumer, not merely adding an unused renderer. Label receiving/loaded subset/interrupted/legacy separately; “complete material” is not tool success, final reply or verification (`interface.md:11`, `NativeActivity.tsx:47–49`). Only a compatible new descriptor can replace the legacy “remainder unavailable” message; historical prefix-only content remains unavailable, with no fabricated reconstruction. SDK public JSON is not the original network encoding. Existing Terminal defaults to ANSI interpretation (`terminal.tsx:229–230`) and copies its entire output prop (`124–131`); supply literal escaped React text for arbitrary SDK JSON/text (the existing NativeBody pre is safe), no innerHTML/auto-open links, and label Copy as loaded/displayed content unless the full body is verified. Preserve user scroll/focus on Load More, readable error/retry, 390/light/dark/keyboard and no hidden/redacted thinking retrieval.
