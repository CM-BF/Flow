## 1. Existing authority and the actual reuse boundary

- `execution-profiles/catalog.ts:5–20,39–78`: one connection owns an explicitly refreshed paged directory with stable subscribe/getSnapshot, stale/error retention, abort plus generation, refresh/loadMore/dispose. It is already a suitable small read module; no new fetch client, timer, registry or draft store is necessary. Its old codec at `24–36` expects unwrapped legacy profiles, so the new protocol needs its own public codec, not a cast or retry through the old reader.
- `selection.ts:20–22,40–59,64–78`: ProfileSelection describes **conversation creation**, not the next message. Its legacy controls check requires fixed-disabled thinking and unsupported effort, and its creation helper pins the baseline configuration. New message-settings catalog controls differ. Passing a new profile through readDirectoryProfile/configuredSelection would reject a valid new declaration; weakening these old checks would silently widen old consumers.
- `ExecutionProfilePicker.tsx:9–17,32–59,65–85`: a controlled value/callback UI already uses the local Button/Radix Dialog wrappers and per-instance useId. Only dialog visibility is local. Locked creation follows a separate rendering branch. Reuse those primitives and style classes; keep creation locked. A new named message-settings leaf must not relabel the old base model as the current message's requested model.
- `App.tsx:369–374,486–495,531–546,949–956`: catalog lifetime belongs to the connection, profile selection uses stable view.key, and current draft/view maps are the retention authority. The independent leaf will own none of these maps. Reusing the creation profileSelections map as a second per-message draft store would be wrong.
- `ConversationThread.tsx:79–94,100–129,158–174,176–181`: current profileReason deliberately accepts a locked creation. That is not a per-message capability check. Submit captures material/intent/text before composer.send; onNew hands ownership synchronously to the existing outbox/queue receipt before awaiting completion. Both Send and Queue use this path. Future settings must be captured at that same pre-await boundary and carried through the original receipt; not reread from UI/catalog after material preparation.
- `outbox.ts:10–30,67–86,89–106`: the outgoing type/request reconstruction currently includes text and material refs but no messageSettings. It generates and retains creationKey/turnKey, then retry uses the same receipt. This must be extended by the future owner, not bypassed by a picker issuing a POST.
- `queue/commands.ts:44–64,98–106,112–130`: enqueue already freezes its input and owns a single key. Its existing local legacy ACK checks do not cover new settings. The shared public opt-in queue decoder is the authority to consume later; do not implement another Web settings matcher.

## 2. Minimal leaf interface and responsibilities

**Directory:** add a named `createMessageSettingsCatalog(reader)` export in the existing catalog module. The private reader accepts the existing after/limit/signal shape and returns the **public** ClaudeMessageSettingsCatalogPage. It ultimately delegates exactly once to the fixed shared `FlowClient.claudeMessageSettingsProfiles` method. Before that public method is published, an injected typed test port is sufficient only if the exact approved public types/schema have been made available through a controlled fixed input. No locally redefined wire DTO, manual header/fetch, any-cast or moving contract import.

Share the existing pagination/lifetime implementation behind the two public factories (one small private helper, protocol-specific decode functions and independent snapshots). Preserve the old ExecutionProfileCatalog API and behavior. Each protocol instance remains connection-bound; never mix its pages, cursors or rows with another protocol's cache. Explicit refresh/loadMore only; no render-triggered read. Public schema plus current cursor/order validation rejects an entire bad page, wrong protocol, duplicate/nonadvancing cursor or invalid tuple; retain the previous page as stale without clearing a user's selected value.

**Selection:** add pure `captureMessageSettings` / eligibility helpers in selection.ts using the published claudeTurnSettingsSchema, canonical helper and checkClaudeTurnSettingsAllowed. Inputs are the candidate public snapshot, current trusted public capability/profile reference and current decoded policy; output is a detached recursively frozen public snapshot or an explicit actionable invalid reason. There is no stored selection, receipt, scheduler or HTTP operation here. The caller owns the draft. Optional absence means omit messageSettings; it is distinct from any explicit not-requested effort/speed tuple. Empty choices is not an implicit default. Local validation is a new-send preflight, not center authorization or permission to retry an already frozen command.

**UI:** add a separately exported controlled `MessageSettingsPicker` in ExecutionProfilePicker.tsx. Props carry the directory snapshot, current optional public snapshot, eligibility/current profile context, and onChange/refresh/loadMore callbacks. Its only mutable UI state is disclosure/dialog visibility. It renders each configured **complete tuple** as an atomic choice (at most 32 per policy); never compose independent model/thinking/effort/speed controls into a combination that was not published. Display the selected tuple's requested.model, not profile.model.value/configuration.model. Keep unknown/stale/empty/error visible and the selected value retained. A user may explicitly clear the next-draft opt-in; no refresh or old ACK clears it automatically. Reuse existing Dialog semantics and style classes; no new slot, host, command authority or dependency.

Root's fixed contract audit establishes: snapshot canonical <=1024 UTF-8 bytes; choices 0..32 complete unique tuples with their public total bound; exact id/runnerId/configDigest tie; no goal-tools/activeSteering policy co-enablement; configured choices do not prove provider entitlement/availability. Follow these public checks, rather than reproducing schema rules in JSX. This leaf only presents the next draft's requested value. Historical requested and SDK observed remain separate future consumer work; absent/null/alias/cooldown are never backfilled from the selection.
